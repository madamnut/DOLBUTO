# 주 화면 지형의 CPU 명령 기록 비용 · 2026-10-01

AI 작업 컨텍스트. 사용자 `ㅇㅋ 실시`로 일반 지형과 LOD의 호출 수/CPU 시간 계측 및 렌더 거리12/24/32 비교, 빌드·패키징을 승인했다. 간접 그리기·버퍼 통합·컬링 변경은 이번 범위가 아니다.

## 구현 및 측정 범위

`--profile-gpu gpu.csv --profile-draws draws.csv`로 명시적으로 활성화한다. `DrawStats`에 실제 draw/descriptor bind/vertex bind/push 호출 수를 저장하며 일반 지형과 LOD 각각 시작/종료 타이머를 한 번씩 사용한다. CSV는 전 프레임을 저장하고 기존 GPU CSV와 frame/steady로 조인할 수 있다. CPU CSV의 해상도·렌더 거리는 프레임별로 보관한다. 기본 GPU CSV 형식은 바꾸지 않는다.

CPU 시간은 단순 Vulkan 함수 호출 시간만이 아니라 다음 구간의 벽시계 시간이다.

- 일반 지형: 파이프라인/atlas 연결 → 컬럼·청크 순회 → 빈 메시/시야 제외 → 좌표/선택 표시 준비 → push/descriptor/draw → 물/얼음 목록 구성.
- LOD: 파이프라인/환경 연결 → coverage 연결 → 타일 순회·메시 맵 조회 → 근거리 중복 제외·시야 제외 → 타일 push → 분할 버퍼별 bind/draw.
- GPU 실행·큐 제출/대기·월드 준비/업로드·그림자·플레이어·투명체의 별도 draw·UI는 CPU 두 구간 밖이다. CPU와 GPU는 겹쳐 실행되므로 합산해 FPS로 해석하지 않는다. CPU에는 OS 스케줄링 지연과 계측 자체의 작은 비용도 들어간다.
- 새 옵션이 없으면 새 타이머 읽기/카운터 증가/CSV 누적이 없다. 자동 테스트/CTest/CU/합성 입력을 추가하거나 사용하지 않았다.

draw 계측은 기존 near ready 조건과 함께 LOD 생성 대기0, paused/memory_limited=false, 최신 scene revision의 GPU 업로드 완료를 요구한다. 이후240프레임을 예열하고600steady프레임을 측정한다. 미완료는 부분 CSV를 보존하고 exit1이다. 기존 GPU 단독 프로필 조건은 유지한다.

## 해석 및 후속 제안

- 거리32에서 주 화면 지형 CPU 두 구간 합은 약1.17ms다. 이는 최적화로 모두 없어질 비용이 아니며 CPU 전체 프레임 시간이나 제출 시간도 아니다.
- 세 거리 모두 LOD 구간 CPU 시간이 더 크다. LOD는 호출 수가 더 적어도 모든 active 타일을 순회하고 메시 맵을 조회한다. 현재 코드는 근거리와 겹쳐 제외할 타일도 메시 조회를 먼저 한다. 이 순회/조회와 명령 기록은 현재 타이머로 분리되지 않았으므로 호출 수 자체가 주원인이라고 단정할 수 없다.
- 후속 우선 후보는 LOD의 그릴 목록/메시 접근 정리와 배칭이다. 일반 지형도 거리32에서0.54ms로 증가해 장거리에서는 함께 검토할 가치가 있다. 다중 간접 그리기만 바꿨을 때의 절감량은 아직 측정하지 않았다.
- CPU에 보이는 목록을 만들고 이를 간접 명령으로 전달하는 첫 단계는 GPU 컬링/새 그림자 알고리즘을 요구하지 않는다. 공유 버퍼·타일 데이터 표·수명 관리가 필요하며 이후 별도 승인 범위다. 물/얼음의 순서 및 그림자 경로를 섞어서 한 번에 변경하지 않는다.
