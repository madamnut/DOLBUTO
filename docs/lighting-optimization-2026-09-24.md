# 조명 최적화와 비교 · 2026-09-24

AI 작업 컨텍스트. 사용자 `실시` 승인으로 조명 작업 생략/재사용, 데이터 접근 단순화, 밝기별 큐와 독립 비교를 적용했다. 지형/밝기 규칙/컬럼 공개 스케줄링/사용자 설정은 유지했다. 아래 성능은 이 PC/현재 입력의 측정치이며 보편적 배율이나 FPS 향상 보장이 아니다.

## 구현

- `local_column_light`: X가 연속인 순서로256개의 수직 하늘빛 상태를 계산한다. 균일 고체/균일 직사광 공기는 배열 일괄 채움으로 처리한다. 발광원이 없는 컬럼은 인공광 시작점 탐색을 생략한다. 균일 밝기 청크의 내부에서는 전파가 시작될 수 없으므로 세로 경계만 검사한다. 동등성이 증명된 위/아래 청크까지 균일하면18³ 임시 halo를 만들지 않는다.
- `LightUpdate`: 청크별 블록/밝기 배열 포인터와 균일 값을 작업 시작에 캐시한다.9개 이웃 인덱스도 한 번 준비해 경계/dirty 처리의 반복 hash 조회를 줄인다. 원본 불변 snapshot은 수정하지 않고 실제 변경 청크만 복사한다.
- 경계 검사: 양쪽이 완전 고체이거나, 양쪽 밝기가 균일하고 각 채널 차이가1 이하인16높이 구간은 건너뛴다. 그 시점에 경계로부터 증가할 빛이 없다는 조건이다. 다른 경계에서 들어와 증가한 빛은 기존6방향 전파가 계속 전달한다.
- `LightChunk::has_block_light`는 보수적인 요약이다. 기본값true(미확인), false이면 **halo를 포함한 해당 청크 전체**에 인공광이 없다. 광원 제거 중간에 임의로 false로 바꾸지 않는다. 변경 시 nonzero가 생기면 캐시를 true로 올리고, 완료 결과에서 확인한 뒤 false로 낮춘다. 양쪽이 false인 경계는 인공광 채널을 검사하지 않는다. GPU ABI/빛의4비트 범위는 바꾸지 않았다.
- `finish`:27개 공급 청크의 균일 값/차폐가 일치할 때 즉시 압축 결과를 사용한다. 내부가 바뀌지 않은 청크는 기존 내부 샘플을 복사하고 halo만 다시 샘플링한다. 실제 결과가 같으면 이전 shared_ptr를 유지한다. 월드Y 밖은 기존밝기0/15·비차폐, 준비되지 않은 이웃은 기존 halo fallback을 그대로 따른다.
- 전파 증가 큐:0..15 밝기별 bucket, 높은 밝기부터 처리. 이미 더 밝아진 오래된 큐 항목은 무시하고 밝기1은 이웃을 증가시킬 수 없으므로 재등록하지 않는다. 감소 전파는 기존 순서를 유지한 연속 vector 큐다. 감소가 전부 끝난 뒤 후보의 **현재 밝기**로 증가 bucket을 구성한다. 감소 전의 밝기로 미리 정렬하면 잘못된 결과가 될 수 있다.
- 명시적 SIMD/AVX/SWAR를 추가하지 않았다. 일반 Release 컴파일러의 최적화는 유지한다. `light_diagnostics.hpp`의 큐/작업 카운터는 비교 대상에만 컴파일되며 일반 게임에서는 제거된다.
- 동기 CPU 진입점 `update_column_lights`를 LightWorker와 비교 도구가 공유한다. 도구만 별도 알고리즘을 실행하고 게임은 다른 경로를 실행하는 구성을 피했다.

## 비교 방식

- 선택적 `lighting_benchmark`는 EXCLUDE_FROM_ALL이며 CTest/일반 빌드/게임 시작에 연결하지 않는다. 사용자 승인 범위의 독립 비교다. 컴퓨터 유즈나 키/마우스 입력 합성 없음.
- `tools/benchmarks/lighting/baseline.inc`는 변경 전 lighting.cpp를 동결한 기준 구현이다. 원래 알고리즘은 유지하고 동기 호출 wrapper와 선택적 카운터만 추가했다. `reference.cpp`에서 공개 함수/worker 이름을 바꿔 같은 실행 파일 안에서 현재 구현과 비교한다. 공통 공개 자료형에는 새 보수적 metadata 필드가 있으나 기준 구현은 이를 이용하지 않는다. 후속 작업에서 이 기준 알고리즘을 조용히 수정하지 않는다.
- 환경: Windows11, i5-13400, RTX3080, Clang23.1.0 Release. 단일 호출은 단일 스레드이며 두 구현을 같은 프로세스에서 순서를 번갈아 실행한다. affinity/전원 정책/우선순위는 변경하지 않았다.3회 워밍업 후31회×독립 실행2번=각 구현/상황당62표본. 원시1860관측. 입력 생성·사전 조명 준비·정확성 비교·카운터 수집·파일 출력은 시간 측정 밖이다. 호출 내 임시 할당/출력 생성/해제는 포함한다.
- 현재 사용자 worldgen SHA256 `964ABA96CC5E6D75653D7C265E0DAD0F4E85CD47650DEA53873E951560742C9D`, settings `F264819A6441F5C47B27920DF650A3721F29E2B9C9252F61FA260B3E23052A30`. 이전 world-profile 문서의 보관 입력과 동일하며 작업 전후 보존했다.
- 초기 지형은 이전 계측과 같은 바다/육지/굴곡 원점이다. 초기 작업1회는 **3×3컬럼의 내부 조명9회+중앙 컬럼의 이웃 연결1회**, 블록 생성 제외다. 균일 공기/고체/물은 동일한 처리량의 추가 입력이다. 실제 스트리밍은 모든 표시 컬럼의 이웃 연결을 하므로 이 배율을 전체 로딩에 그대로 곱할 수 없다.
- 편집 작업1회는 준비된9컬럼 snapshot에 변경 묶음을 적용하고 변경된 컬럼/halo를 구성하는 전체 조명 update다. 순수 flood 루프 시간만이 아니다. 모든 편집 표본은 사전 조명 계산을 시간에서 제외한다.
- 동굴은 Y64..79 공기층, Y80..95 고체 천장. 개방은 한 수직 통로의 천장16블록 제거, 폐쇄는 통로 아래 한 블록 차단이다. 광원은 밝기15, 중첩 광원 제거 및 X/Z컬럼 모서리/순환 경계를 포함한다. 물은 기존 물을 제거하는 입력이며 설치 불가능한 물을 편집 API로 억지 추가하지 않는다.

## 정확성

- 최종 두 실행 모두 각123,731,712개, 합계 **247,463,424개 샘플 위치**에서 하늘빛/인공광을 담은 바이트와 차폐 bit가 정확히 일치했다. 각 청크 내부뿐 아니라 전체18³ halo를 비교한다. 키와 revision도 비교한다. 인공광 없음 요약이false일 때 실제 모든 샘플의 인공광이0인지 확인했다. 허용 오차나 픽셀 유사도 비교가 아니다.
- 기본6상황/편집9상황 외에2컬럼만 있는 부분 이웃 입력, Y0/511, 순환좌표,48묶음×12개 시도하는 고정 seed 혼합 편집을 포함한다. 각 편집의 결과를 다음 snapshot으로 이어 받아 추가·제거·중첩을 반복한다. 공기/고체/발광만 편집하며 게임에서 거부하는 요청은 예외로 중단한다.
- 기준과 현재가 일치한다는 검증이지 기준 알고리즘의 모든 물리적 정확성이나 가능한 월드 전체를 증명한 것은 아니다. RGB/움직이는 물/새 감쇠 규칙은 범위 밖이다.
- 탐색 실행 run1/run2/final1에는 게임이 허용하지 않는 물 설치 항목이 있어 최종 통계에서 제외했다. 거부된 fixture를 실패로 처리하고 기존 물 제거로 바꾼 final-a/final-b만 보고한다. 게임의 물 설치 규칙을 바꾼 것이 아니다.

## 전체 파이프라인과 실제 게임

- CPU WorldStream은 변경 전후 실행 파일로 반경6/113컬럼,3지역, 계측ON/OFF 각3회씩 실행했다. 전체 출력 면 수는 지역별116037/79149/108220으로 모두 동일했다. 계측OFF의 평균은 바다396.37→258.93ms, 육지413.68→270.12ms, 굴곡312.64→241.47ms였다. 기존 실행의 부스트/백그라운드 변동이 커서 이 숫자를 정밀한 인과 배율로 취급하지 않는다. 순차 before 배치 후 after 배치이며 위 단일 호출 교대 비교보다 통제가 약하다. 원시 표본을 보존한다.
- 실제 게임은 설정 사본과 변경 전후 바이너리를 `build/release/light-runtime`에서 일반 CLI로 실행했다. 바다 원점7040/5504, 렌더 거리24,1793표시컬럼/1993데이터컬럼, VSync OFF/FPS무제한, 사용자 그래픽 설정을 유지했다. 순서는 before/after, after/before, before/after로3쌍이다. 입력/카메라 이동을 합성하지 않았다.
- 전부1793컬럼 공개 및 관련GPU fence 회수 완료. 총 face bytes13008216 동일. 런타임 exit0, 오류 로그0. Release validation=0이므로 validation layer 검증 성공을 주장하지 않는다.

worker 값은 병렬 작업 경과시간 합이며 전체 로딩 벽시계 시간과 다르다. 실게임 조명 구성은 local과connect의 비율이 독립 조명 벤치마크와 다르므로 배율도 다르다. 전체 공개 평균 차이는약1.5%로 작고 표본3쌍/실행 변동 범위의 영향을 받는다. 조명 계산이 크게 줄어도 전체 로딩이5배 빨라진 결과는 아니다. 이전에 확인한 단일 incoming·다음 prepare의 수령/공개와 GPU프레임 길이가 여전히 영향을 준다. 공개 파이프라인 변경은 이번 승인 범위에 포함하지 않았다.

## 재현과 보관

1. 개발 환경 로드 후 `cmake --build --preset release --target lighting_benchmark`.
2. `build/release/bin/lighting_benchmark.exe out/Sandbox/worldgen.json <출력 디렉토리>`를 명시적으로 실행한다. 성능 측정 전에 해당 상황의 값 비교를 통과해야 진행한다. 기록에 실패한 요청을 섞지 않도록 별도 폴더를 사용한다.
3. 이번 출력은 `build/release/light-compare-2026-09-24/final-a`, `final-b`, `pipeline-before`, `pipeline-after`, `game24-*.csv/.log`. 변경 전 실행 파일도 동일 작업 디렉토리에 보존했다. build 정리 시 사라지는 임시 자료다.
4. `python tools/benchmarks/lighting/summarize.py build/release/light-compare-2026-09-24 docs/benchmarks`로 요약한다. 이번 고정 폴더/실험 구성의 집계 도구다.
5. `docs/benchmarks/lighting-2026-09-24-*`에1860개 timing 관측, 작업량, 두 번의 정확성 보고, 게임 실행별 결과/worker 합, 파이프라인 통계를 보존한다. 설정 입력은 world-profile-2026-09-24의 보관본을 따른다.

후속 최적화는 이 결과를 기준으로 결정한다. 일반 자동 테스트를 복구하거나 기준 알고리즘을 현재 구현으로 대체하는 승인은 아니다.
