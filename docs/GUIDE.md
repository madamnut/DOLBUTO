# 개발 기록 가이드

이 문서는 개발 기록을 작성하는 기준을 정리한다.

## 프로젝트

- 개발 언어는 C++이며, C++20을 기준으로 한다.
- 그래픽 API는 Vulkan을 사용한다.
- 빌드 시스템은 CMake와 Ninja를 사용한다.
- 빌드 구성은 `Debug`와 `Release`만 사용한다.
- 창 생성과 입력 처리는 GLFW를 사용한다.
- 최종 목표는 마인크래프트류 샌드박스 복셀 게임이다.
- Vulkan SDK는 로컬 설치본을 사용한다.
- GLFW는 Windows 바이너리 배포본을 받아서 사용하는 방식을 기준으로 한다.

## 개발 원칙

- 기능을 한 스크립트나 한 파일에 몰아넣지 않는다.
- 렌더링, 엔진 코어, 월드, 복셀, 입력, 리소스, 플랫폼 처리 등은 역할에 맞게 분리한다.

## 구현 규칙

- 구현 전에 관련 파일과 기존 구조를 먼저 확인한다.
- 현재 요구사항을 만족하는 가장 단순한 형태로 구현한다.
- 파일, 클래스, 함수는 역할과 책임 기준으로 분리한다.
- 한 파일에 여러 책임을 몰아넣지 않는다.
- 단, 분리를 위한 분리는 하지 않는다.
- 새 추상화, 공용 시스템, 외부 라이브러리는 필요성이 명확할 때만 추가한다.
- 미래에 필요할 것 같은 기능은 지금 구현하지 않는다.
- 구현 후에는 현재 목표에 필요한 변경인지, 더 단순하게 만들 수 있는지 확인한다.

## 빌드와 런타임 경로

- Debug 빌드는 기존 개발 경로를 사용한다.
- Debug 빌드의 `assets`, `config`, `saves/world`는 프로젝트 루트의 폴더를 직접 참조한다.
- Debug 빌드의 shader는 CMake 빌드 폴더의 컴파일된 `.spv`를 사용한다.
- Release 빌드는 실행 파일 옆의 `assets`, `config`, `shaders`, `saves/world`를 사용한다.
- Release 출력 폴더는 폴더째 이동 가능한 포터블 실행 단위로 본다.
- Release 배포 확인은 반드시 Release 출력 폴더에서 직접 실행해서 확인한다.
- 빌드는 반드시 사용자가 직접 수행한다.

## 디렉터리

버전별 개발 기록은 `docs/{version}/` 아래에 날짜별 Markdown 파일로 작성한다.
`docs/design/`은 Obsidian으로 관리하는 현재 구현 기준의 설계/기획 문서 영역으로 사용한다.

```text
docs/
  GUIDE.md
  design/
    index.md
  0.0.0.0/
    SUMMARY.md
    YYYY-MM-DD.md
  0.0.0.1/
    YYYY-MM-DD.md
```

예시:

```text
docs/0.0.0.0/2026-05-01.md
```

## 파일 규칙

- 파일명은 `YYYY-MM-DD.md` 형식을 사용한다.
- 작업이 없는 날은 파일을 만들지 않는다.
- 같은 날짜에 여러 작업을 했더라도 하나의 파일에 누적한다.
- 버전이 변경되면 새 버전 폴더를 만들고 같은 규칙을 따른다.
- `docs/design/` 문서는 날짜별 개발 로그가 아니라 현재 구현 기준 설계 문서로 작성한다.
- 구현이 바뀌면 관련 `docs/design/` 문서도 함께 갱신한다.

## 설계 문서

`docs/design/`은 Obsidian 디렉토리이며, 게임 플레이, 월드, 렌더링, 저장, 플레이어, 디버그 도구 등 현재 구현된 시스템을 기획/설계 관점에서 정리하는 공간이다.

- 개발 로그처럼 시간순으로 적지 않는다.
- 현재 시스템이 어떻게 동작하는지 기준으로 작성한다.
- 아직 구현되지 않은 아이디어를 적을 수 있지만, 현재 구현과 명확히 구분한다.
- 코드 구조가 바뀌거나 기능이 제거되면 관련 문서도 갱신한다.
- 버전별 작업 기록과 섞지 않는다.
- Obsidian에서 읽기 쉽도록 짧은 문서 단위로 나누고, 관련 문서는 `[[문서명]]` 링크로 연결한다.
- 문서 파일명과 링크명은 가능하면 한글로 작성한다.

## 일일 기록 형식

날짜별 기록은 아래 형식을 기본으로 사용한다.

```md
# YYYY-MM-DD

## 작업 기록
- 작업하면서 진행한 내용을 시간순으로 적는다.

## 결정 사항
- 구조, 기술, 방향성에 대한 결정을 적는다.
- 결정 이유가 있으면 함께 적는다.

## 이슈
- 막힌 점, 버그, 나중에 확인할 내용을 적는다.
```

## 섹션 규칙

### 작업 기록

작업 중 계속 갱신하는 영역이다.

- 구현한 기능
- 수정한 코드
- 조사한 내용
- 테스트하거나 확인한 내용

### 결정 사항

나중에 다시 봤을 때 이유를 알아야 하는 판단을 기록한다.

- 엔진 구조
- 렌더링 방식
- 외부 라이브러리 선택
- 빌드 시스템 방향
- 코드 스타일이나 프로젝트 규칙

### 이슈

당장 해결하지 못했거나 추적이 필요한 내용을 기록한다.

- 버그
- 빌드 문제
- 성능 문제
- 조사 필요 항목
- 보류한 작업

## 버전 갱신 절차

버전을 올릴 때는 아래 순서를 따른다.

1. 코드와 문서의 버전 표기를 새 버전으로 갱신한다.
2. 이전 버전 폴더에 `SUMMARY.md`를 작성한다.
3. 새 버전 폴더를 만든다.
4. 새 버전 폴더에 날짜별 작업 로그를 만든다.
5. 저장 포맷이나 실행 호환성에 영향이 있으면 반드시 기록한다.
6. 빌드는 사용자가 직접 수행한다.
