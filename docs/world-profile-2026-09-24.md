# 청크 생성 병목 계측 · 2026-09-24

AI 작업 컨텍스트. 사용자의 명시적 `실시`로 기존 알고리즘에 선택적 타이머를 추가하고 실제 실행했다. 생성 규칙, 저장 설정, 스레드 수, 스케줄링, 조명 알고리즘, 렌더 예산은 바꾸지 않았다. 노이즈 교체/최적화 승인이 아니다.

## 결론

- 현재 설정에서 노이즈 연산은 병목이 아니다. 렌더 거리24의 생성 worker 누적 작업 시간에서 2D/워핑/3D를 모두 합쳐 약0.32~0.52%, 2D+워핑만 약0.03~0.04%다.
- 생성 연산의 주요 비용은 조명 약57~71%와 블록 배열 생성 약19~32%다. 조명은 실제 flood fill보다 경계 전수 검사와 조명 halo 구성/압축 비용이 크다.
- 실제 화면 공개에는 렌더 프레임에 묶인 단일 `incoming_` 경로도 영향을 준다. 요청1793컬럼이 모두 공개되기까지 지역별 평균7.31~11.01초다. GPU 업로드 구간은 평균0.0014~0.0016ms/프레임으로 작다. 이것을 PCIe 대역폭 병목으로 설명할 근거는 없다.
- 2D 맵을4D Simplex 토러스로 바꾸는 성능 검토는 타당하다. 다만 현재 코드를 계측한 결과이며 교체본 전체 생성 성능을 직접 측정한 것은 아니다. 현재3D shape의 X/Z 토러스 변환은5D가 필요하므로 기존4D 벤치마크를 적용할 수 없다. 기후 맵/편집기 전체 미리보기/향후 식생에서의 샘플 수 증가도 별도 문제다.

## 환경과 범위

- Windows11, i5-13400, RTX3080. Clang23.1.0 Release, 기존 FastNoise2/FastSIMD 자동 dispatch. 실제 게임과 동일하게 WorldStream4worker, MeshLightWorker1개를 사용한다. CPU affinity/전원 정책/프로세스 우선순위는 변경하지 않았으며 백그라운드 부하와 부스트를 완전히 통제하지 않았다.
- 원본 `out/Sandbox/worldgen.json` SHA256: `964ABA96CC5E6D75653D7C265E0DAD0F4E85CD47650DEA53873E951560742C9D`.
- 원본 `out/Sandbox/settings.json` SHA256: `F264819A6441F5C47B27920DF650A3721F29E2B9C9252F61FA260B3E23052A30`. 작업 전후 동일. VSync OFF/프레임 제한0/TAA OFF, 그래픽 품질은 사용자 설정 복사본이다. 창 기본 논리 크기1280×900, 고DPI 허용. CLI 일반 실행만 했으며 창/입력을 자동 조작하지 않았다.
- 실행 복사본은 `build/release/profile-game`. 게임 자체 CLI로 월드 진입, 원점 선택, 완주 종료를 한다. 카메라/플레이어 이동과 편집을 합성하지 않는다. 고정 위치 신규 로딩 측정이며 이동 중 취소/재요청/캐시 재사용 성능을 측정한 것은 아니다. 시작 메뉴/셰이더 준비 시간은 로딩 시간에서 제외한다.

## 생성 작업의 비용 분해

반경24/3회 합산. 분모는 generation/local_light/connect_light/mesh/scheduler 루트 작업의 소요 시간 합이다. 병렬 worker의 **경과 시간을 누적**한 비중이며 OS CPU cycle/전체 로딩 벽시계 시간의 비중이 아니다. 중첩 타이머는 exclusive 값으로 빼서 중복 집계하지 않았다. 작업 중 선점/잠금 대기는 포함될 수 있다. 화면/GPU/packing 시간은 이 분모 밖이다.

나머지는 task 스케줄링/객체 구성/표면 규칙 등의 작은 비용이다. 순수 noise API 구간은 매우 짧아 타이머 오버헤드와 선점에 민감하므로 소수점 이하를 정밀한 하드웨어 성능 수치로 해석하지 않는다. warp는 두 변위 노이즈뿐 아니라 좌표 변환/버퍼 준비도 포함하는 보수적인 범위다.

소스상의 비용 원인:

- `lighting.cpp::LightUpdate::connect`:9컬럼 안의 인접 경계를 매번 높이512 전체에 걸쳐 양쪽 광 채널로 검사한다. 현재 자연 생성에는 발광 블록이 없고 넓은 균일 영역이 많아 실제 전파가 거의 없어도 이 검사는 수행한다.
- `local_column_light`와 `LightUpdate::finish`: 각 세로 청크의18³ 조명/차폐 샘플을 구성·비교·압축한다. 임시 local halo와 이웃 연결 후 halo의 비용을 합친 항목이다.
- `terrain.cpp::generate_chunk`: 밀도 보간·재질 판정·배열 저장 및 균일성 검사를 수행한다. `find_surfaces`도 별도로 수직 표면을 찾는다. 3D 샘플 일부를 두 경로에서 계산하지만 **샘플 호출 비용 자체**의 비중은 작았다.
- 이 결과는 자연 생성 초기 로딩에 한정된다. 동굴/인공 광원/블록 편집 이후의 제거·추가 전파에서는 flood fill 비중이 달라질 수 있다.

반경24,3회. 전체 공개 시간은 첫 request 이벤트부터 마지막 published 이벤트까지다. 평균 / 중앙값 / 관측 최대, 단위초.3표본에서는 p95도 최대이므로 장기 꼬리 지연의 신뢰구간으로 취급하지 않는다.

- 요청→완성은 연산뿐 아니라 큐/이웃 의존성/8컬럼 admission window 대기를 포함한다. `task_wait`는 이미 enqueue된 작업의 대기만 측정하므로 아직 admission되지 않은 시간을 포함하지 않는다. 두 값을 합산하면 중복이다.
- `WorldView::prepare`는 `incoming_` 한 컬럼을 완료하고 다음 프레임에 다음 컬럼을 받는다. packing 작업의 수령도 다음 prepare부터 가능해, 관측상1793컬럼 처리에약3700~3800프레임이 사용됐다. 후반 GPU 프레임이 길어지면 이 공개 통로도 느려진다. 가까운 순서/컬럼 동시 공개 규칙은 유지한 채 여러 컬럼을 파이프라인에 넣는 방안은 **후속 제안**, 아직 구현하지 않았다.
- GPU 수치는 기존 timestamp query를 읽는다. 업로드 값은 begin_frame~finish_uploads 사이 명령/동기화를 포함하므로 순수 전송 대역폭이 아니다. 마지막 in-flight 몇 프레임의 timestamp는 재사용 시 읽지 못해 집계에서 빠진다.
- `gpu_retired`는 해당 submission fence가 완료됐음을 CPU가 확인한 시점이다. 실제 GPU 완료 순간보다 늦으며 디스플레이 scanout/눈에 보인 순간을 측정한 것은 아니다.

같은 반경24의 CPU 전용 하네스(계측OFF)와 비교하면 다음과 같다. 평균 / 중앙값 / 관측 최대, 단위초. CPU 하네스는 stream 생성부터 worker 종료까지 포함하지만 실제 게임 표는 request부터 공개까지이므로 완전히 같은 구간의 차감 실험은 아니다. 실행 시점과 부스트도 다르므로 차이를 모두 업로드 경로 비용으로 단정하지 않는다.

|---|---|---|
| 바다권 |5.796 /5.812 /5.838|11.013 /11.001 /11.110|

게임 측 작업별 기록/현재 단일 incoming 제어 흐름과 함께 보면, 특히 바다권/굴곡 지역에서 생성 계산만으로 전체 공개 지연을 설명하기 어렵다. 다만 프레임 제한 해제/다중 incoming을 실제 적용한 인과 비교는 아직 하지 않았다. 반경24 ON/OFF 중앙값 차이는-2.06%/+0.006%/+1.05%이며, 바다권 ON 첫 실행3.770초는 나머지5.692~5.795초보다 빨랐다. 이상값으로 버리지 않고 전부 보존했다.

## 계측 구현과 한계

- 기본 OFF. worker 시작 전에 ON, worker 종료 후 저장한다. OFF일 때 시계 조회/기록 잠금/파일 쓰기 없음. scope 생성의 분기/스택과 일부 함수 호출 비용은 남으며 완전한 컴파일 제거는 아니다.
- 중첩 Scope는 thread-local로 집계하고 루트 작업 종료 시 메모리의 희소 CSV 행 버퍼에 추가한다. 이벤트/루트 저장 mutex, 타이머 호출, 버퍼 확장 비용은 계측 영향이다. 전체 기록은 작업 종료 후 파일에 쓴다. 최대200만 행을 넘으면 성공으로 간주하지 않고 오류를 낸다.
- 초기 탐색 실행은 기록250000개 한도를 넘어 실패했으며 최종 통계에서 제외했다. 기록을 희소 행으로 바꾼 후 전 지역을 다시 완주 측정했다. 첫 CPU 하네스의 publish try_lock 실패 처리도 수정 후 처음부터 재측정했다. 게임 알고리즘 오류나 최적화 수정은 아니다.
- 계측ON/OFF 비교는 같은 바이너리에서 실행 순서를 교대했다. 반경6 중앙값 차이는 지역별-2.90%/-1.08%/+2.91%로 실행 변동과 겹친다. 계측이 게임을 빨라지게 했다는 뜻이 아니며 정확한 오버헤드를 분리하지 못했다. 미세한 최적화 효과 판단에 이 차이를 사용하지 않는다. 모든 반복의 컬럼 수/면 개수는 지역별 동일했다.
- 성능 실행은 일반 자동 테스트가 아니다. CTest/게임 입력 자동화/회귀 테스트를 추가하지 않았다. Release validation은0이므로 로그의 Vulkan errors0은 validation layer 검증 성공과 구분한다.

## 결과 파일

- 원시 작업별 CSV/실행 로그: `build/release/world-profile-2026-09-24`(CPU반경6, 실제 게임6/24), `build/release/world-profile-cpu24-2026-09-24`(CPU반경24). 수백MB의 일시적 원시 기록이며 build 정리 시 사라진다.
